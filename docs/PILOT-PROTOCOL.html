Pilot protocol

The spec's effectiveness gate (section 8) asks for a personal pilot that compares the reminders you use now with COMMAND. This is how to run it. It needs no app feature: COMMAND keeps no rating, and what you write down stays with you. It is one person's experience, so it supports a decision for you, not a claim about anyone else.

Before you start

  1. Install the build named in the release receipt on your own phone, and walk the real-phone checks there (issue #4): it rings after a restart, the voice is loud enough on the speaker, and your phone maker's battery settings leave it alone. If any of these fails, stop and report it: a pilot on an alarm that may not ring measures nothing.
  2. Pick three to five tasks you start most weekdays and tend to put off (for example: begin the main work block, go for the walk, start the evening review). Use the same tasks in both halves.
  3. Set the volume consent and the profile you would really use. Do not change dials during a half unless something is unbearable; if you do, note the day.

Two halves of one week each

HalfWhat reminds youDays
A, baselineWhat you use today (phone alarms, calendar notifications, another app). COMMAND is installed but has no missions.7
B, COMMANDOne COMMAND mission per task at the same times; your old reminders for those tasks are off.7

If you can spare a third week, run A again: a change that comes back when COMMAND goes away is more believable than one that does not.

Each day, about two minutes, at the same time in the evening

One line per task, on paper or in a note on your phone:

Write downHow
Started on timeyes (within 10 minutes) / late (minutes) / not at all
Progressnone / some / most / done
Got back on track after a slipyes / no / no slip
Helpfulness of the reminder1 (in the way) to 5 (it got me going)
Alert fatigue1 (fine) to 5 (I dread it)

In half B, COMMAND's History shows what you reported to it (started, done, skipped, missed). Use it to check your memory, not instead of your own line: it only knows what you told it.

At the end of each half

  • Count, per task: on-time starts, days with progress, days done, recoveries.
  • Answer two questions: Would I keep using this? and Did it make any day worse?

Stop early if

  • An alarm fails to ring, rings at the wrong time, or cannot be silenced at once. Report it with the time; that is a reliability bug, not a pilot result.
  • It costs you sleep, or you notice more stress than help on three days running. That answer is a result in itself (the spec's "hold or narrow").

What to report back

Only the counts and the two answers, for example "on-time starts 9 of 25 in A, 16 of 25 in B; fatigue 2 to 3; would keep it: yes". Task names, times and notes stay with you: the repository is public. The spec reads the result as go (starts improve at a bearable cost), revise (you answer alarms but do not start more) or hold (more stress than use).
