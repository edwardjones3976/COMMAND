Project COMMAND · public repository

Reconstruction design

Context

Project COMMAND is a consent-driven Android execution director: at a scheduled time it must ring in a way that is hard to ignore, demand a deliberate handshake, speak one instruction, ask a one-tap status later, and recover humanely (docs/PRODUCT-SPEC.html v3.1). The current app (android/app, package com.example, 18,251 Kotlin lines, exported from Google AI Studio) does not deliver that loop: the alarm receiver only posts a notification (service/ReveilleAlarmReceiver.kt:17-21); MainActivity sits over the lock screen unconditionally (AndroidManifest.xml:30-31); session state lives in a ViewModel field (viewmodel/CommandViewModel.kt:106); the database is v6 with exportSchema = false and fallbackToDestructiveMigration() (data/CommandDatabase.kt:67-68,85); seed data fabricates a streak with 125 credits and "Google Calendar" missions (data/CommandRepository.kt:55-77,94-114); calendar import invents events (service/GoogleCalendarSyncService.kt:143-147,227-272); voice packs carry false licence claims (CommandRepository.kt:722-728,751-757,767-786); Gemini receives titles with no opt-in and caches fallback text (service/CommandAiService.kt:48,158-173); the App Check debug provider ships in release (app/build.gradle.kts:114); the reCAPTCHA site key is a tracked resource (res/values/firebase_applet_config.xml:3). The 21 open GitHub issues (#2–#27) trace to these roots.

Intended outcome: a from-scratch on-device rebuild delivering spec P0 + P1 + P2, reusing the proven voice pipeline, every claim bound to a named test or an owner sign-off, delivered as small PRs that each leave main installable, under AGENTS.md (one writer per worktree, Cursor review, Cursor merges, no force-push).

Owner decisions (2026-11-02), fixed:

  • On-device rebuild (Room, alarms, scheduling, coaching, voice) plus opt-in Firebase cloud sync (off by default; history never leaves the device).
  • Scope P0 + P1 + P2; no desktop companion, no P3/P4.
  • Deterministic local coaching and local Android TTS always work offline; Gemini Studio voices and AI directives are opt-in, pre-rendered, with local TTS fallback.
  • Extras kept, aligned to the spec: directors mapped onto the six personalities; streaks become honest recovery-friendly history (no credits, badges, buy-backs); fabricated telemetry and the soundboard go; Preset Studio becomes the five presets plus seven dials.

Fixed constraints: applicationId = com.aistudio.command.vtxrpl (namespace becomes com.command); reuse VoiceMastering.kt, VoiceDirectorEngine.kt (GeminiSpeechSource seam, nowMs clock), DirectorBriefs.kt and tests VoiceAudioTest, StoneVoiceVerificationTest, GeminiTimeoutTest, StoneAudioRegressionTest, CapturingAudioTrack, oldchain/; JDK 21 / Gradle 9.3.1 / AGP 9.1.1 / Kotlin 2.2.10 / compileSdk 36 / minSdk 24; Windows dev box, emulator command_api36 only (no physical device: real-device gates are owner-signed, issue #4); local-only android/local.properties, android/app/google-services.json; the voice must be loud (issue #2).

How this plan was produced

Three independent architectures (reliability-first, product/UX-first, maintainability-first) → three judges (spec, platform, delivery) → synthesis from the reliability-first base with 30+ grafts → three adversarial critics (60 gaps: 1 blocker, 32 major, all resolved) → revision. The full design and its decisions log were produced by the multi-agent workflow; this document is the binding, condensed version.

  • M4a review fixes (PR #32): stopping a ring never starts a service. The RingController port carries the occurrence's request code; the Android implementation cancels that occurrence's notifications and tells the running service through an in-process RingSession, and ReveilleService ends with stopSelf(startId), so a stray stop can no longer race a foreground start. The service handles deliveries one at a time and checks each against the database before it touches a ring that is going: a stale or repeated alarm leaves the sound alone, a valid later one takes over the sound (the earlier occurrence stays as it was), durable steps are never cancelled half-way, and an end that arrives before the check finishes is remembered. Ring cycles are timed on the monotonic clock, and a restart within the same boot goes on from the stored monotonic deadline (SessionPlan.elapsedMs), not from the wall clock. The check for an end that arrived while the service was still reading the mission title comes after that read, with nothing in between, and a start whose startForeground fails is still answered with a minimal foreground notification before the fallback ring is posted. When the plan runs out inside the service it posts the same quiet missed note as the cycle-end alarm. The fallback ring notification is tagged by occurrence (id 4), is cancelled when the ring ends, never rings for an expired plan, and carries its own sound before Android 8. Acknowledge and StartGuidance commit together, and an occurrence left acknowledged is moved on when reopened. The hold is timed on the frame clock, so turning animations off cannot turn it into a tap, and Back is consumed while the alarm rings. Known limit: the degraded path is silent when notifications are denied; its event says so (notified=false) and the M5 reliability screen warns about the combination.
  • M4b cut-over notes: unfired occurrences are a plan derived from the mission, so an edit keeps the ones whose time did not change, discards the rest (OCCURRENCE_DISCARDED, no tombstone, so an undone edit leaves nothing in the way) and creates what is missing; a delayed child survives an edit and goes with a deletion. "Test this alarm now" uses one hidden mission (builtin_test_mission, category TEST) and a real alarm five seconds ahead. Opening the app runs AppStartup: channels, the legacy import, cancelling the previous version's alarms by their old component and request code (and its notification channel), then MissionRepository.refreshWindow (seven days of occurrences, every armed alarm put back, and an alarm more than ten minutes overdue recorded as missed while the phone was off). A one-off is scheduled however far away it is; a repeating mission gets seven days, or, when that week is empty, its next occurrence however far away, so every saved mission has a row to open, edit or delete. Editing or deleting a mission removes its unfired occurrences in the same transaction as the mission change (an alarm that is only just overdue and not yet delivered included, the platform alarms are cancelled after the commit), and a second test ring replaces the first. The schedule is two separately bounded lists (upcoming, recent). The importer commits its done-marker with the imported rows and cannot run twice at once, and the previous version's alarms are only counted as cancelled once its database could be read. The old app's strings, images and receivers are gone, and PublicationSafetyTest now fixes the exact set of exported components. Checked on the API 36 emulator with a database in the previous version's format placed before the first launch (the previous version's APK itself was not installed): the import, arming, a test ring over the lock screen, an edit that leaves the armed alarm alone, a real unattended ring on its scheduled second that times out into the missed note, resume, start, creating and deleting. Two findings from that run are fixed in this milestone: a ring that ran out was labelled "Alarm silenced" (it now says "Alarm missed"), and the editor's line about a fixed mission promised a confirmation that the rigidity setting may not ask for.
  • Reconcile notes (M5a): M5 is split in two: M5a is the engine described here, M5b the screens (onboarding, Reliability, Consent Center); together they close #6 and #16. One MissionRepository.reconcile(trigger) replaces refreshWindow. ArmingReconciler first records what the platform allows and then reconciles; it runs when the app opens, from ReconcileAlarmsWorker (queued, expedited, by SystemEventReceiver for boot, app update, clock set, zone change and a change of the exact-alarm permission; the receiver only queues the work, holding its broadcast open until WorkManager has stored the request, because Android 15 does not let a boot receiver start the media-playback service and a receiver must not open the database) and from a six-hourly backstop that every run makes sure exists (its first run is one period after it is queued). One run: each enabled manual mission gets exactly its next week (an occurrence at a time the rule no longer gives is discarded, a missing one is created and armed); every armed occurrence is asked after with a FLAG_NO_CREATE probe (AlarmScheduler.isArmed), a missing alarm is logged as ALARM_LOST{trigger} (a floor: the probe sees the PendingIntent, and Android 12 can drop a revoked app's alarms and leave it, so false is proof and true is not), and every armed alarm is put back either way (arming replaces); an occurrence more than ten minutes overdue becomes Miss(DOWNTIME) and its one MISSED_WHILE_OFF event carries late_s (the Miss command carries how late it is); one that is only just due is armed again with its own time and Android delivers it within about five seconds (6.2 s measured on the API 36 emulator). A quiet open or periodic run writes nothing; boot, update, clock, zone and permission runs always leave BOOT_RECONCILE{trigger, created, discarded, rearmed, lost, missed, precision_changed, repaired} (repaired is a stored occurrence that had never been armed). PreconditionProbe only reads (exact alarms, notifications, ring-channel importance, full-screen intent from Android 14, alarm-stream audibility, battery optimisation, background restriction, standby bucket); PreconditionRecorder writes each changed value as PRECONDITION, a flipped permission as PERMISSION_CHANGED plus a system-sourced consent row, a newly silent alarm stream as DND_MAY_SUPPRESS, and keeps the last reading in settings.permission_snapshot; the first reading is a baseline, not a change, and the comparison is made again inside the transaction that writes, because after a force-stop the platform delivers a boot broadcast just as the app opens and two readings can arrive together (found in review; PreconditionRecorderTest runs two at once and fails without it). The worker's getForegroundInfo names no service type: a type would need the data-sync permission and a Play declaration for a service that never starts on the versions that require them (expedited work uses a foreground service only before Android 12); its notification id is negative (AlarmContract.ID_RECONCILE), so that it can never replace a ring, whose id is its occurrence's request code. Verified on the API 36 emulator (debug and noexact builds, signed with the same key, installed over each other): the update delivered MY_PACKAGE_REPLACED and the worker wrote the baseline reading and BOOT_RECONCILE{PACKAGE_REPLACED} without the app being opened; a cold restart of the emulator with seven armed alarms ended with seven ALARM_LOST, BOOT_RECONCILE{BOOT, lost 7, rearmed 7} and all seven alarm-clock entries back 13 s before the first of them, which then fired 2.5 s after its time (an adb reboot of the headless emulator never came back, so the restart was a hard one); after a force-stop the platform delivered BOOT_COMPLETED again when the app was next launched and the same path put the alarms back; a revoked exact-alarm permission (noexact, appops deny) killed the app and its exact alarms and the next open recorded PERMISSION_CHANGED, a system consent row and seven ALARM_LOST{OPEN}, then put all seven back inexact (plain RTC_WAKEUP, arm_mode INEXACT), and granting it again queued EXACT_ALARM_CHANGED and made them exact; a time-zone change moved a daily 04:00 mission's seven occurrences two hours in UTC so they stayed at 04:00 local (created 7, discarded 7) and changing back restored them; revoking and granting notifications was recorded as PERMISSION_CHANGED and system-sourced consent rows. An alarm that was only seconds overdue when the app came back (its alarm dropped by a force-stop) was armed again and rang 6.2 s later; two reconciles arriving together (the boot broadcast and the app opening) made Android deliver it twice, and the state machine rejected the second delivery (REJECTED_TRANSITION) without touching the ring. Not exercised on a device: the clock being set (the receiver mapping is unit-tested; setting the clock needs root), a muted alarm stream (this image's alarm stream cannot go below 1, so the probe is unit-tested), the six-hourly backstop, and the Android 12-13 revocation flow. On API 36 dumpsys alarm does not print a PendingIntent's data URI, so an alarm clock is recognised by its showIntent.

  • Alarm audio notes (M6): A ring now says one line over its tone, in the phone's own speech engine and with nothing sent anywhere. Speaker (:domain: Line of Segments, each flagged when it carries the person's own words; SpeechUsage ALARM or PREVIEW; SpeakResult Spoken, Unavailable(reason) or Interrupted, never an exception) is implemented by LocalTtsSpeaker in :voice (the engine writes the line to a file with TextToSpeech.synthesizeToFile, the WAV is read back, VoiceMastering.master with the existing PREVIEW profile levels it under the -1 dBFS ceiling, and an AudioTrack on USAGE_ALARM plays it; the louder ALARM profile arrives with M9) and by SilentSpeaker for a phone with no engine. The ring never waits for it: the service starts the tone and the vibration first, then Speaker.prepare() (the engine starts alongside the database work, because a cold engine takes seconds), and the line joins when the engine is ready (init is waited for 12 s and synthesis for 15 s; each failure is a SpeechProblem, and anything unexpected that still escapes is caught in the service and logged as UNEXPECTED, because an uncaught exception in a coroutine would kill the process in the middle of an alarm). The tone is turned down to 30 % only when the line is about to be heard (onAudible), so a slow engine never makes the alarm quieter, and back up when it ends; answering, silencing or missing the ring cuts the line off, stops the player and lets the engine go, and a second ring that arrives while one sounds takes over the tone and says its own line. The words are ReveilleLines (string resources, "Time to start: {title}. First step: {first step}.", the person's words in segments of their own and a closing full stop trimmed so it is not said twice); the coaching engine replaces them in M10a. The route policy (settings.alarm_route_policy, speaker and headset by default) governs the line only: with headset only and none connected nothing is said and the log records AUDIO_ROUTE{devices, policy, spoke:false}; the tone and the vibration ring on every route; a line that was said logs AUDIO_ROUTE{..., spoke:true} and one that could not be logs TTS_UNAVAILABLE{reason} (NO_ENGINE, INIT_TIMEOUT, SYNTHESIS_FAILED, PLAYBACK_FAILED, UNEXPECTED). The alarm volume: a fourth consent, VOLUME_CONTROL, owned by the app and off until the person turns it on in the consent center, where an app-owned consent is a switch with its words and an Android-owned one a button to Android's screen (ConsentCenterViewModel.setGranted refuses keys Android keeps, so nothing is recorded that Android does not say). Only with it does AlarmVolumePolicy raise the alarm stream, and nothing else, for the first ring of a run: the old level is written down first (settings.volume_restore); a refusal by the platform (a SecurityException, which Do Not Disturb can cause) is logged as VOLUME_SET_REFUSED and leaves nothing behind; the level is put back when the last ring ends, whoever ended it, unless the person moved it meanwhile (VOLUME_RESTORE_SKIPPED); a restore the platform refuses is logged (VOLUME_SET_REFUSED{phase:restore}) and kept for the next reconcile; and a record left by a ring that died (a force-stop leaves its occurrence FIRING in the database) is undone by ArmingReconciler unless this process's service is ringing something, so opening the app to answer an alarm never turns the alarm down, and a service destroyed with a ring in it restores too. Do Not Disturb is the ninth precondition (DO_NOT_DISTURB: total silence, or priority-only with the alarms exception switched off, which exists only from Android 9, blocks alarms); the probe only reads and never asks for policy access, and the Reliability page says "Blocks alarms" with a button to the sound settings. Verified on the API 36 emulator (debug build, Google TTS with its offline en-US voice): dumpsys audio during a ring shows two started players, both USAGE_ALARM, the tone (CONTENT_TYPE_SONIFICATION) and the line (CONTENT_TYPE_SPEECH), and the log has AUDIO_ROUTE{speaker, SPEAKER_AND_HEADSET, spoke:true}; a cold engine (its app force-stopped) took about six seconds to bind and the first line began about twelve seconds after the tone, because the first synthesis loads the voice model, which is why the first build's four-second bound logged TTS_UNAVAILABLE{INIT_TIMEOUT} and the bound is now twelve; with the engine disabled (pm disable-user --user 0 com.google.android.tts, enabled again afterwards) the log had TTS_UNAVAILABLE{NO_ENGINE} 0.3 s after the ring began and the tone rang alone; switching the volume consent on in the consent center recorded VOLUME_CONTROL granted by the user, and the next ring raised the alarm stream from 6 to 7 within a second of the tone, wrote {original 6, set 7}, and Safety silence from the notification put it back to 6 and cleared the record (every time); a force-stop in the middle of such a ring left the alarm stream at 7, the record in place and the occurrence FIRING (nothing finishes a ring that died, which is an M4a and M5a gap left for a follow-up), and opening the app put the volume back to 6 and cleared the record; with total-silence Do Not Disturb (cmd notification set_dnd none) the Reliability page said "2 things can stop an alarm" (alarm volume silent, Do Not Disturb blocks alarms) and the log recorded PRECONDITION{DO_NOT_DISTURB, blocks_alarms, from free}, and priority-only with the default exceptions read as free again; an unattended ring still ended as MISSED at the end of its plan and Safety silence from the notification still ended a ring as SAFETY_SILENCED. Not exercised on a device: the headset-only route (the emulator has no headset; ReveilleServiceSpeechTest covers it with a fake), the person lowering the volume during a ring and a platform that refuses a volume change (the shell cannot set the alarm stream on this image; AlarmVolumePolicyTest covers both with a shadow that refuses), Android 17's background-audio hardening (risk 7: it needs an API 37 image, a download the owner has not been asked for), real hardware, and how loud the line is on a real speaker (owner sign-off; M9 owns loudness).
  • M6 review fixes (PR #36): Three reviews (Cursor, Codex and Copilot) raised some twenty points between them, each checked against the code before anything was changed; one was answered without a change (below). *The person's words only reach a voice that works on the phone.* AndroidSpeechSynthesizer keeps the engine's own voice when it is installed and works offline, otherwise switches to the best installed offline voice of the person's language, and when there is none says nothing (SpeechProblem.NO_OFFLINE_VOICE, TTS_UNAVAILABLE); an engine that does not list its voices cannot be shown to work offline and says nothing either, and a voice whose data is not installed is never used (it can start a download). Nothing is handed to the engine before that choice. The engine sits behind a small TtsEngine interface, so this and the rest of the logic around the engine are unit-tested; the real TextToSpeech wrapper is checked on a phone, and logs which voice speaks and whether it needs a network (never the words). *A headset-only line is kept to a headset.* Speaker.speak takes the RoutePolicy; AudioTrackPlayer pins a headset-only line to a headset output before it is made audible (HeadsetDevices.playbackTarget: wired, USB, hearing aid, low-energy, then Bluetooth audio; never Bluetooth's call channel, never the speaker), watches the track's routing and stops it that instant if the platform moves it elsewhere (a headset pulled out), reporting HEADSET_REQUIRED, and plays nothing at all when there is no headset to pin it to. Not exercised on a device: the emulator has no headset. *One line at a time through the engine, and an abandoned line is stopped in the engine.* synthesize takes a mutex; a line that is cancelled, times out or fails calls engine.stop() before the next is handed over; letting the engine go ends the wait for a line in flight. LocalTtsSpeaker counts the lines asked for, so a later line supersedes an earlier one that is still being prepared (the earlier is Interrupted and never becomes audible), and the service stops the speaker whenever one ring takes over from another. *The same alarm delivered twice leaves the ring that is going alone*: it used to be taken for a restart, restart the cycles and say the line again. *The raised volume changes hands.* raiseFor runs for every ring that takes over, and when the alarm stream is already at its highest because an earlier ring of the run raised it, the restore record is adopted by the new ring; the earlier ring's clean-up, queued on a background scope and so able to run after the next ring has begun, then finds a record that is not its own and leaves the volume alone (the tests for this, for the takeover and for the duplicate delivery were run against the code without each fix and failed). A restore is read back: the platform keeps an app without its privileged audio permission above a floor of its own, which the normal MODIFY_AUDIO_SETTINGS permission that one reviewer suggested is not, as far as could be established, what lowers, so it was not added; when the level that comes out is not the level wanted, the log says what was wanted and what came out (VOLUME_SET_REFUSED{phase:restore, wanted, got}). *Do Not Disturb is read from the consolidated policy* from Android 11 (the call does not exist before it; lint caught that the first version assumed Android 9), which folds in an automatic rule that is active now; on Android 9 and 10 the ordinary policy is all there is; the probe is still what Android reports and not a model of any phone maker's extras. Smaller: a title ending in ? or ! is not given a second full stop when spoken; the WAV reader's chunk walk adds in Long, so a huge chunk size ends the walk instead of wrapping round; the consent switch is announced with its title; HEADSET_REQUIRED is used; and the comments that said the line 'never needs a network' now describe what is enforced. *A later automated review (Codex, on f0d6143) found one more, and it was right:* restoreAnySoon(), which the end of a ring and the destruction of the service queue on the policy's own scope, put the volume back unconditionally, so if the next ring had begun and raised or adopted the volume by the time the queued work ran, it was put back under that ring (the occurrence-specific restore was already protected by the change of owner, this path was not).
