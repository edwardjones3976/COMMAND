Permissions

From the merged release manifest (android/app/build/intermediates/merged_manifest/release/, every module and library merged in). CI fails if this list and that manifest differ in either direction (scripts/receipt-permissions.py check, in the assemble job). So this list follows the current main manifest, which CI enforces, and not only the tree and digests above: CAMERA was added after them (M13a, amendment 40).

  • android.permission.READ_CALENDAR: the optional calendar import, asked for on its own screen, read only.
  • android.permission.CAMERA: only for the QR handshake, after the camera consent; frames are decoded on the phone and never stored. Declared by the app itself (amendment 40); CameraX merges in no permission of its own, only a disabled, unexported configuration service. The camera is not required, so a phone without one can install the app.
  • android.permission.SCHEDULE_EXACT_ALARM (up to API 32) and android.permission.USE_EXACT_ALARM: exact alarm clocks. The app asks the platform before every arm and falls back to an inexact alarm, and says so, when refused.
  • android.permission.POST_NOTIFICATIONS: the ring and check-in notifications.
  • android.permission.USE_FULL_SCREEN_INTENT: the ring screen over the lock screen.
  • android.permission.FOREGROUND_SERVICE, android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK and android.permission.FOREGROUND_SERVICE_SYSTEM_EXEMPTED: the ring's foreground service (media playback at run time; the other type is declared so that it can be swapped).
  • android.permission.WAKE_LOCK: keeps the phone awake for the length of a ring.
  • android.permission.RECEIVE_BOOT_COMPLETED: re-arms the alarms after a restart.
  • android.permission.VIBRATE: the ring's and the voice cues' vibration.
  • android.permission.INTERNET, android.permission.ACCESS_NETWORK_STATE and com.google.android.providers.gsf.permission.READ_GSERVICES: added by the reCAPTCHA library under Firebase App Check (ACCESS_NETWORK_STATE also by WorkManager, which reads the network state and sends nothing). See the next paragraph.
  • com.aistudio.command.vtxrpl.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION: added by AndroidX Core, signature level, so that only this app can reach its own runtime receivers.

INTERNET is declared, and no code that runs uses it. The Firebase libraries stay because Gemini, Studio voices and cloud sync come back after this receipt, each behind its own consent. Today: the App Check setup (configureAppCheck) has no caller; Firebase's start-up provider finds no Firebase configuration in a build without google-services.json, so Firebase never starts; and NoNetworkInRuntimeCodeTest fails if the app's own code gains a way to the network. Measured on the API 37 emulator: the release build ran for 45 s with no traffic recorded for its uid by dumpsys netstats, no socket of its uid in /proc/net, and no Firebase start in the log.

Android 17: background-audio hardening, measured before any targetSdk change

Plan risk 7. On the API 37 emulator, enforcement was forced on with cmd audio set-hardening enable and then throw (on this image the command is set-hardening; the plan's set-enable-hardening does not exist there). With the volume consent given and the alarm level at 6 of 7:

  • The ring works in both modes: foreground service and an alarm-usage player started. The raise 6 to 7 took in four runs out of five; in one CI run (enable and throw alike) the platform dropped it, silently or with the exception. The raise now reads the level back and tries again for about two seconds while the ring sounds, and logs VOLUME_SET_REFUSED{phase:raise} with nothing left on record if it never takes; before, the dropped raise left a record that the restore later took for a change the person made. Whether the retry is enough on Android 17 is for the nightly runs to show.
  • The restore after a ring that died is dropped. The ring's process was force-stopped mid-ring, so only the stored record was left; the next start of the process runs the reconcile from a background worker with no foreground service, and the platform ignored its volume change (AS.HardeningEnforcer: AudioHardening volume control ... ignored), without an error in enable mode and with an IllegalStateException in throw mode.
  • Found and fixed here. The app read the level back, saw it unchanged and took that for the platform's floor, so it cleared its record and the alarm volume would have stayed at the highest for good. In throw mode the exception escaped the restore and the whole reconcile after the restart failed and was retried, re-arming included. Now an unchanged level and that exception are both a refusal: VOLUME_SET_REFUSED{phase:restore} is logged, the record stays, and the level is put back when the app is next opened (measured: back to 6 in both modes) or by any later reconcile the platform allows. The reconcile no longer fails.
  • On the first enable run the force-stop also crashed this emulator image's system server (a SIGSEGV in the input-method service's package monitor, not in this app); the next runs did not.

So the ring needs no change for Android 17, and targetSdk can go to 37 later, with this run repeated then. What remains: on Android 17 a ring that is killed leaves the alarm volume raised until the app is opened.

Known limitations

  • Nothing has run on a real phone: ringing across restarts and days of standby, loudness through a real speaker, headset and Bluetooth routing, phone makers' battery killers, TalkBack (issue #4; the listening of issue #2).
  • Four handshakes, not P1's seven; speech is the phone's own engine; no Gemini, Studio voices, cloud sync or P2. All are coming back.
  • From DC1: a cancelled exception of a synced calendar series needs two calendar reads before its alarm goes, so it can still ring if due before the second; refused alarms past the Schedule's 200 upcoming rows show only on Reliability; the time picker's AM/PM is clipped at the largest font.
  • On Android 17, a ring killed mid-way leaves the alarm volume raised until the app is opened (above).
  • The reliability harness shows an alarm armed from deep idle firing on time, not one firing while the device is still in deep idle; it does not drive the locked-screen swipe; a silent alarm stream (volume 0) needs a real phone; occurrences.ring_mode is never written.
  • The reCAPTCHA site key, an AI Studio screenshot and working notes remain in git history (no force-push); rotating the key or rewriting history is the owner's decision.

Installing and rolling back

  1. Before replacing a build, export your data: Settings, Your data, copy. There is no import yet, so this copy is a record, not a way back in.
  2. Take the apks artifact of a green CI run of main and check its SHA-256 against that run's summary. Install the debug APK (adb install -r app-debug.apk, or open it on the phone with installs from this source allowed). The release APK from CI is unsigned and will not install as it is.
  3. Today a later build will not install over an earlier one: each CI run signs with a throwaway key of its own, and Android refuses a different key (measured: INSTALL_FAILED_UPDATE_INCOMPATIBLE ... signatures do not match). Uninstalling removes every alarm and the history. The phone signing identity below ends this.
  4. Rolling back: with the same identity, install the earlier APK over the later one (adb install -r -d). Every build so far has versionCode 2 and database version 1, so an earlier build opens the later one's data. Once a later build raises the database version, rolling back past it means uninstalling.

One signing identity for the owner's phone (proposal)

The build already takes one: with COMMAND_SIGNING_KEYSTORE (a path outside the repository), COMMAND_SIGNING_STORE_PASSWORD, COMMAND_SIGNING_KEY_ALIAS and COMMAND_SIGNING_KEY_PASSWORD set, the debug, noexact and release builds all sign with that key (the Play upload key, if one is ever set, still wins for release). Without them nothing changes. Measured on the API 37 emulator with a throwaway key: the release build installed over the debug build in place (first-install time kept), and a build signed with another key was refused.

  1. Someone with the repository's admin rights creates one keystore (for example keytool -genkeypair -keystore command-phone.p12 -storetype PKCS12 -alias phone -keyalg RSA -keysize 3072 -validity 10000) and keeps it, with its password, outside the repository and backed up: a lost key means every later build needs an uninstall.
  2. They store it as four repository secrets: COMMAND_SIGNING_KEYSTORE_B64 (the file, base64), COMMAND_SIGNING_STORE_PASSWORD, COMMAND_SIGNING_KEY_ALIAS, COMMAND_SIGNING_KEY_PASSWORD. The assemble job then signs the APKs of every build of main with it and prints the certificate; the keystore is written to the runner's temporary folder and never uploaded. A pull request's build runs code nobody has merged yet, so it never gets the key and stays on a throwaway one.
  3. The phone's current install has a throwaway key, so the first build with the identity needs one last uninstall (export first). After that, every build updates in place.

The publication-safety test fails if a keystore (.jks, .keystore, .p12, .pfx) is ever tracked, and .gitignore lists them.
